Lost Files

notes/lost-files/ — note

Problem

RecentTab shows what's new. But what about something disappearing again - deleted, moved, renamed? Until now: nothing at all. The file was there, then it wasn't, without a trace.

What we deliberately didn't build

A genuine live watcher (Windows can do this, via ReadDirectoryChangesW) would have reported every deletion instantly. That would need its own, permanently running background process per folder - clearly more effort than the benefit justifies here.

We also looked at the Recycle Bin. Possible in theory, but deleted files land there under mangled names, the real name only sits hidden inside an index file. And permanent deletions (Shift+Delete) never show up there at all.

The solution

Simple comparison: on every normal refresh, the new list gets compared against the last one. Whatever's missing counts as "lost" - without claiming to know whether it was deleted, moved, or renamed. We simply don't know that, and we don't pretend to.

Not a live event, but a window: "was there at the last refresh, isn't now." With a 5-minute interval, that means sometime in the last 5 minutes, not down to the second.

For each lost entry, whatever was known at the moment it was last seen stays around: name, size, modified and created dates, which watched folder, which recording session. A small dedicated window shows this - TC's normal properties dialog would just fail, the file doesn't exist anymore.

The search-again button

Maybe the file isn't gone at all, just moved. One click asks Everything system-wide for the exact name - no folder restriction, deliberately. If something turns up, the text in the same window just gets appended to, nothing new opens. If nothing turns up, it was likely a genuine deletion.

A matching name alone proves nothing though - README.md could exist in a dozen unrelated folders. So strict by default: only a match with the exact same size and the exact same modified date counts as confirmed. LostSearchStrict=0 turns that off, for the case where the file was edited again after moving - size and date would have genuinely changed then, and the strict check would wrongly doubt a real match.

Open in TC

Select some text in the info window, click "Open selection in TC" - and exactly that selected piece opens as a new tab in the opposite panel. Deliberately selectable, not just the whole path at once: paths are hierarchical, sometimes you want to jump three levels up and look around yourself, not straight to the (possibly no-longer-existing) original folder.

Runs through an officially documented command-line call (totalcmd.exe /O /T /L= or /R=), not an internal TC message - no reliable, documented way to do it that way was ever found. Three settings make the behavior adjustable instead of locking in the one approach built first: LostOpenTarget (opposite or active panel), LostOpenMode (new tab or replace the current one), LostOpenNewWindow (a separate TC instance instead of the running one).

Lost files are tied to the recording history they came from - a reset clears both together, not just the history. A currently active recording is deliberately not stopped by this, only its start time jumps to now - otherwise files already shown before the reset would immediately get reported as "lost" again, since the comparison would still find them in the old, otherwise discarded list.
